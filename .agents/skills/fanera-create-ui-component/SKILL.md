# Общий UI-компонент Fanera

Соблюдай наставнический режим корневого `AGENTS.md`: не пиши код за разработчика без явной просьбы. Для разрешённой реализации сначала прочитай `docs/design/component-map.md`, `docs/design/README.md`, `apps/web/src/shared/components/ui/index.ts`, CSS-тему и подходящий раздел `docs/system-design`.

1. Найди нужный элемент в карте, затем открой соответствующий слой актуального Penpot: светлая и тёмная темы, варианты, состояния, размеры и токены. Проверь уже готовые компоненты в `apps/web/src/shared/components/ui` и их public API. Если подходящий компонент есть, используй его; новые пропсы добавляй только для подтверждённой потребности.
2. Если подходящей реализации нет, но макет есть, реализуй компонент по Inspect и свойствам слоёв, а не по памяти или названию. Переиспользуй `Button`, `Icon`, `Avatar`, `Dialog`, `Toast` и прочие доступные общие элементы. Для иконок сверяй страницу `Иконки` и используй установленный `lucide-react` через общий `Icon`, когда это соответствует макету.
3. Если нет отдельного образца, проверь экраны и UI-kit ещё раз. Для нового визуального паттерна сначала согласуй макет с командой: статус `нет / нет` не даёт права придумывать утверждённый дизайн. При расхождении кода и макета зафиксируй различие и уточни, что актуально.
4. Сохраняй границы FSD и экспорт через public API. Применяй смысловые токены CSS, локализацию пользовательского текста, `Toast` для уведомлений и `ConfirmDialog` для разрушительных действий. Новые зависимости — только после согласования с командой.
5. Проверь основной сценарий и важные крайние случаи тестами по правилам репозитория; сравни компонент со слоями Penpot и в Storybook в обеих темах. Обнови `docs/design/component-map.md` ссылкой на реализацию и честным статусом соответствия. Отметь непроверенные состояния отдельно.

Карта — маршрут к источникам, а не замена их проверки. Код может содержать дополнительные варианты, не представленные на макете; не приписывай им утверждённый дизайн без проверки.
