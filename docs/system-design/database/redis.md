# Redis: схема ключей

Два отдельных инстанса с разными настройками (см. [README §1](README.md#1-какие-хранилища-и-почему)):

| Инстанс | `maxmemory-policy` | Персистентность | Почему отдельно |
|---|---|---|---|
| **realtime** | `allkeys-lru` (можно вытеснять) | не нужна | presence и кэш восстановятся сами, pub/sub вообще не хранит данных |
| **queue** | **`noeviction`** (требование BullMQ) | AOF `everysec` | вытеснение ключа очереди = потерянная задача |

> В пет-проекте это один Redis с `noeviction`: проще, и при маленьких объёмах вытеснение не понадобится.

## realtime

| Ключ | Тип | TTL | Назначение |
|---|---|---|---|
| `presence:{boardId}` | HASH `userId → {name, color, instanceId, lastSeen}` | поле обновляется heartbeat раз в 15 с; ключ удаляется при пустой доске | список «кто на доске» для REST, превью в каталоге («3 человека сейчас тут»). Сами курсоры здесь **не хранятся** |
| `perm:{boardId}:{userId}` | STRING `owner\|editor\|viewer\|none` | 60 с | кэш итоговой роли для handshake и REST. Сбрасывается сообщением `perm:changed`. Периодическая перепроверка открытых сокетов (раз в 30 с) этот кэш **не** использует: иначе потерянное событие продлило бы старую роль ещё на 60 с |
| `rl:{scope}:{userId\|ip}:{window}` | STRING (INCR) | длина окна | rate limit REST (`@nestjs/throttler` + Redis storage). Лимиты WS-событий считаем **в памяти процесса**: сокет живёт на одном инстансе, ходить в Redis на каждый курсор незачем |
| `ai:quota:{userId}:{yyyymmdd}` | STRING (INCR) | 48 ч | дневная квота ИИ: атомарный `INCR`, при `> 20` — 429. Если задача упала, делаем `DECR` (возвращаем квоту) |
| `board:home:{boardId}` | STRING `instanceId` | 30 с, продлевается | (опционально) на каком инстансе «живёт» доска при board affinity |

> `Idempotency-Key` здесь **не** хранится: этот Redis вытесняет ключи и не персистентен, а потеря ключа превращает повтор запроса в новое создание. Ключи лежат в core, в таблице `idempotency_keys` (Р-38).

**Pub/sub каналы:**

| Канал | Кто публикует → кто слушает | Что |
|---|---|---|
| `socket.io#/collab#...` | `@socket.io/redis-adapter` (служебные) | доставка `io.to(room).emit()` сокетам на других инстансах. Публикуется **каждая** рассылка, даже если все адресаты локальные. Сейчас — обычный адаптер (Р-44). При росте — шардированный (Redis 7 sharded pub/sub): в режиме `dynamic` у комнаты свой канал, и процесс подписан только на комнаты, где у него есть сокеты |
| `collab:doc:{boardId}` | collab-инстанс → другие collab-инстансы, у которых открыт этот `Y.Doc` | правки доски для **серверных** копий документа (adapter доставляет только клиентам). Плюс досинхронизация после разрыва Redis: `{type: 'sync', from, stateVector}` → ответ с диффом для `from` (Р-35) |
| `perm:changed` | api → все collab | `{boardId, userId?}` — пересчитать роли или отключить сокеты |
| `user:events` | api / worker → collab | `{userId, event, payload}` — `ai:done`, `notification:new`, `comments:changed` и т. п. → в комнату `user:{id}` или `board:{id}` |

## queue (BullMQ)

> **Правила jobId.** В custom jobId **нельзя двоеточие**: BullMQ сам использует его как разделитель в ключах Redis. Поэтому разделитель — `-`. Задача с тем же jobId не добавится, **пока она хранится в Redis**, в том числе завершённая (`removeOnComplete: {count: 1000}`). Для разовых задач (ИИ, картинка, копирование) это и нужно. Для повторяющейся компакции — нет: следующая компакция доски молча не поставилась бы. Поэтому у компакции не jobId, а встроенная дедупликация.

| Очередь | Дедупликация | Хранить завершённые | Concurrency | Ретраи |
|---|---|---|---|---|
| `ai` | jobId `ai-{requestId}` | последние 1000 | 25 на процесс (I/O-bound) | 2, экспоненциальный backoff, только на 429/5xx/таймаут |
| `images` | jobId `img-{fileId}` | последние 1000 | = числу ядер (CPU-bound, sharp) | 3 |
| `compaction` | `deduplication: { id: 'compact-{boardId}', keepLastIfActive: true }`: пока задача ждёт, новая не создаётся; если правки пришли во время выполнения, после неё будет ровно одна повторная | не храним (`removeOnComplete: true`) | 4 | 5 |
| `versions` | jobId `ver-{boardId}-{bucket30min}`; если задачу уже вытеснили и она поставилась снова, воркер видит auto-версию за этот бакет в `board_versions` и выходит | последние 1000 | 4 | 5 |
| `board-copy` | jobId `copy-{requestId}` | последние 1000 | 2 | 3 |
| `restore` | jobId `restore-{requestId}`; воркер вызывает collab-инстанс доски ([deep-dive §5](../deep-dive.md#5-восстановление-версии-пока-другие-работают)) | последние 1000 | 4 | 3 |
| `notifications` | jobId `tg-{notificationId}`: только отправка в Telegram, in-app уведомления создаёт релэй сам (Р-41) | последние 1000 | rate limiter BullMQ: ≤ 25 сообщений/с (лимит Telegram ~30/с на бота) | 5, уважаем `retry_after` из ответа Telegram |
| `maintenance` (repeatable) | имя расписания | 1 | — (следующий запуск по расписанию). Задачи: purge корзины (раз в час), прореживание версий (раз в сутки), reconciler зависших задач и неотправленных в Telegram уведомлений (раз в минуту), чистка `pending`-файлов и `idempotency_keys` старше 24 ч |
