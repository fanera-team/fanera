# Словарь: имена в коде и термины из разбора

> Две части. **Первая** — общий словарь фронта и бэка: как называем сущности продукта в коде, API, событиях и БД. **Вторая** — технические термины для фронтендера, который заходит в бэкенд. 🖥 — аналогия из мира фронтенда.

## Часть 1. Имена в коде: общий словарь фронта и бэка

Одну и ту же вещь легко назвать тремя способами: фронт пишет `shape`, бэк — `node`, в БД лежит `item`. Через месяц уже никто не уверен, одно ли это. Поэтому у каждой сущности одно каноническое имя, и оно одинаковое везде: в типах из пакета `contracts`, REST, событиях сокета, таблицах и UI-коде.

🖥 Это как договориться о названиях пропсов в дизайн-системе: `variant`, а не где-то `type`, а где-то `kind`.

**Правило:** нужно новое понятие — сначала добавляем его в эту таблицу (PR с ревью от фронта и бэка), потом пишем код. Колонка «Не называем» — имена, которые на ревью считаются ошибкой.

### Сущности

| Понятие | В коде | Не называем | Комментарий |
|---|---|---|---|
| Рабочее пространство | `Workspace` | Team, Org, Space, Project | группирует доски и участников |
| Участник воркспейса | `WorkspaceMember` | — | связь «пользователь + воркспейс + роль» |
| Приглашение в воркспейс | `WorkspaceInvite` | InviteLink | по email, живёт 7 дней |
| Доска | `Board` | Canvas, Whiteboard, Page | **canvas** — это холст как вид на фронте (рендер, pan/zoom), в данных его нет |
| Ссылка-приглашение на доску | `ShareLink` | Invite, InviteLink | по ссылке, роль `editor` или `viewer`. Не путать с `WorkspaceInvite` |
| Участник доски | `BoardMember` | Collaborator | явная роль на доске |
| Роль | `Role`: `owner` · `editor` · `viewer` | admin, member, guest, reader | итоговая роль — самая сильная из ролей в воркспейсе, на доске и по ссылке. Роли `commenter` нет: комментировать может и viewer (Р-50) |
| Документ доски | `BoardDocument` | BoardState, Data | Y.Doc со всеми элементами. Хранится в collab DB |
| Элемент | `Element` | Shape, Node, Item, Object, Widget | любой объект на доске. **Shape** — один из типов элемента, а не синоним |
| Тип элемента | `ElementType`: `sticky` · `text` · `shape` · `image` · `connector` · `group` · `frame` | note, sticker, card; arrow, line, edge | стрелки и линии — это `connector` со стилем |
| Концы соединителя | `from` · `to` | source/target, start/end | ссылки на `elementId`, а не координаты |
| Группа / фрейм | `group` / `frame` | — | группа — логическое объединение без своей рамки; фрейм — видимая область, внутрь которой кладут элементы |
| Правка | `update` (событие `doc:update`) | patch, op, delta, change | бинарный дифф Yjs |
| Версия | `BoardVersion`, вид `auto` · `named` · `pre_restore` · `pre_ai` | Snapshot, Revision | версию видит пользователь в истории |
| Снапшот | `snapshot` | — | **внутренняя** склейка лога правок при компакции. Пользователь его не видит. Не путать с версией |
| Присутствие | `presence` | online, users | кто сейчас на доске |
| Курсор, выделение | `awareness` | cursor events | эфемерное состояние участника, не сохраняется |
| Тред комментариев | `CommentThread` | Discussion, Conversation | привязан к элементу или точке |
| Комментарий | `Comment` | Message, Note, Reply | ответ в треде — тоже `Comment` |
| Привязка треда | `anchor`: `element` · `point` | position, target | |
| Тред решён | `resolved` | closed, done, archived | |
| Упоминание | `mention` | tag, ping | |
| Файл | `File` | Asset, Attachment, Upload | картинка на доске — элемент `image` с полем `fileId` |
| Запрос к ИИ | `AiRequest` | Job, Task, Prompt | Job — это задача BullMQ, не сущность продукта |
| Черновик ИИ | `AiSuggestion`, статусы `pending` · `applied` · `rejected` · `expired` | Draft, Proposal, Result | применить — `apply`, отклонить — `reject` |
| Уведомление | `Notification` | Alert, Message | |

### Действия, которые легко перепутать

| Действие | В коде | Чем отличается |
|---|---|---|
| Удалить доску в корзину | `trash` (поле `deletedAt`) | можно вернуть 30 дней |
| Вернуть доску из корзины | `restore` (`POST /boards/{id}/restore`) | |
| Удалить окончательно | `purge` | вернуть нельзя. Не `hardDelete`, не `destroy` |
| Восстановить версию | `restoreVersion` (`POST /boards/{id}/versions/{versionId}/restore`, событие `version:restored`) | это не возврат из корзины: применяет старую версию как новую правку |
| Отменить своё действие | `undo` / `redo` | только на клиенте, только свои действия. С историей версий не связано |

### Как называем в разных слоях

| Где | Формат | Пример |
|---|---|---|
| Типы и классы TS | `PascalCase` | `CommentThread`, `ShareLink` |
| Поля JSON в REST и сокете | `camelCase` | `boardId`, `expiresAt` |
| Пути REST | существительные во множественном числе, `kebab-case` | `/boards/{boardId}/share-links` |
| Таблицы и колонки БД | `snake_case`, таблицы во множественном числе | `board_share_links.expires_at` (в Prisma — `@map`) |
| События сокета | `сущность:действие`. От клиента — команда (`doc:update`), от сервера — что произошло (`version:created`, `board:kicked`) | `comments:changed`, `file:ready` |
| ID | uuid | ID элементов и комментариев генерирует клиент |
| Время | ISO 8601 в UTC | `2026-11-10T09:30:00Z` |

## Часть 2. Технические термины

### Совместное редактирование

| Термин | Что это | 🖥 Аналогия |
|---|---|---|
| **CRDT** (Conflict-free Replicated Data Type) | структура данных, копии которой можно менять независимо, а потом слить. Результат всегда одинаковый, конфликтов слияния нет | как `git merge`, который **никогда** не говорит «conflict»: правила слияния зашиты в саму структуру |
| **Yjs** | самая популярная JS-библиотека CRDT. Типы `Y.Map`, `Y.Array`, `Y.Text` | «Zustand-стор, который сам синхронизируется между вкладками и пользователями» |
| **Y.Doc** | документ Yjs: корень, в котором лежат все типы | корневой объект стора |
| **update** | бинарный дифф изменений (`Uint8Array`) | как JSON Patch, только бинарный и коммутативный |
| **state vector** | «что я уже видел»: по счётчику на каждого автора | как `ETag` / `If-None-Match`, только для слияния: «вот что у меня есть, пришли остальное» |
| **awareness** | эфемерное состояние участника (курсор, выделение, имя) из `y-protocols`. В документ не попадает | как `onmousemove` → `postMessage` другим вкладкам, без сохранения |
| **UndoManager** | стек undo в Yjs, отслеживает только транзакции с указанными origin (то есть свои) | `history` в редакторе, но фильтрующий «чужие» изменения |
| **origin** | метка транзакции «откуда изменение» | как `event.isTrusted` или `source` в событии |
| **OT** (Operational Transformation) | альтернатива CRDT: сервер «пересчитывает» конкурентные операции друг относительно друга (Google Docs) | rebase каждой операции поверх чужих |
| **LWW** (Last Write Wins) | при конфликте побеждает последняя запись | `Object.assign` — кто последний, тот и прав |
| **Fractional indexing** | порядок как строки «между» соседями (`a0` < `a0V` < `a1`), чтобы вставка не сдвигала остальных | как `order` во флексе, но без перенумерации всех элементов |
| **Tombstone** («надгробие») | след удалённого элемента в CRDT, нужен для корректного слияния | soft delete на уровне структуры данных |
| **Компакция** | склейка лога мелких правок в один снапшот | как сборщик мусора или `git gc` |
| **Garbage collection (gc) в Yjs** | замена содержимого удалённых элементов компактной меткой «здесь что-то было». Работает только при загрузке в `Y.Doc`; `Y.mergeUpdates` удалённое не убирает | как сборщик мусора в JS: память освобождается, только когда движок реально прошёлся по объектам |
| **Компенсирующая правка** | правка, которой сервер исправляет уже применённые невалидные данные: CRDT-update нельзя «отменить», можно только поверх него записать исправление | как `revert`-коммит в git: историю не переписываем, а добавляем исправление |
| **Версия протокола / схемы** | номер, по которому сервер понимает, совместим ли с ним клиент и в каком формате лежит документ | как `apiVersion` в заголовке запроса или версия в `localStorage`-миграциях |
| **Снапшот** | полное состояние на момент времени | `JSON.stringify(state)` в файл |

### Realtime и сеть

| Термин | Что это | 🖥 Аналогия |
|---|---|---|
| **WebSocket** | постоянное двустороннее соединение браузер ↔ сервер | `new WebSocket()`, который ты уже знаешь |
| **socket.io room** | группа сокетов, которым можно разослать событие разом (`board:{id}`) | канал или топик |
| **namespace** | отдельный «эндпоинт» внутри socket.io (`/collab`) | роут |
| **ack** | подтверждение от получателя (`emitWithAck`). У нас ack на правку = «принято», а не «сохранено» | `await fetch()` вместо «выстрелил и забыл» |
| **`doc:saved`** | событие «правки этого сокета до номера `n` закоммичены в БД». Только от него UI показывает «сохранено» | статус «Saved» в Google Docs, а не момент нажатия клавиши |
| **volatile** | сообщение можно потерять, если клиент не готов | `requestAnimationFrame`-подход: важен последний кадр, а не все |
| **fan-out** | одно входящее событие → рассылка N получателям | один `setState` → ре-рендер N подписчиков |
| **pub/sub** | публикация в канал, все подписчики получают сообщение | `EventEmitter` / `BroadcastChannel`, только между серверами |
| **Redis adapter** | плагин socket.io: рассылка в комнату доходит до сокетов на **других** серверах через Redis pub/sub | `BroadcastChannel` между вкладками, где вкладки — это серверы |
| **Шардированный adapter** | вариант Redis adapter, где у каждой комнаты свой канал, и инстанс подписан только на комнаты, где у него есть сокеты. Обычный adapter доставляет каждую рассылку всем инстансам | подписка на конкретный `queryKey` вместо подписки на весь кэш |
| **Load balancer (LB)** | распределяет запросы по нескольким серверам | — |
| **sticky sessions** | LB отправляет клиента всегда на один и тот же сервер | — |
| **board affinity** | наш вариант sticky: на один сервер направляются все, кто открыл **одну доску** | — |
| **consistent hashing** | способ распределить ключи по серверам, при котором добавление сервера перемещает только 1/N ключей | — |
| **backoff + jitter** | ретраи с растущей паузой (0.5 с → 1 с → 2 с…) и случайным разбросом | то же самое делает TanStack Query в `retryDelay` |
| **stateless / stateful** | сервер не хранит / хранит состояние между запросами (`api` — stateless, `collab` держит `Y.Doc` в памяти) | чистая функция vs компонент со стейтом |

### Надёжность и идемпотентность

| Термин | Что это | 🖥 Аналогия |
|---|---|---|
| **Идемпотентность** | повторный вызов не меняет результат | `PUT` vs `POST`; `Set.add()` vs `Array.push()` |
| **Idempotency-Key** | клиент шлёт uuid запроса, сервер запоминает ответ (у нас — в Postgres, в той же транзакции) и при повторе возвращает его же | защита от двойного клика по «Оплатить» на уровне сервера |
| **Снимок данных (`REPEATABLE READ`)** | уровень изоляции Postgres, при котором все запросы транзакции видят БД в один и тот же момент. По умолчанию (Read Committed) каждый запрос видит свой момент | защита от «tearing» в concurrent React: два куска состояния из одного рендера |
| **Advisory lock** | блокировка Postgres по произвольному числу (у нас — по `boardId`). `xact`-вариант снимается сам в конце транзакции | мьютекс, который нельзя забыть отпустить |
| **at-least-once / at-most-once** | «доставлю минимум раз (могут быть дубли)» / «максимум раз (могу потерять)» | — |
| **Outbox** | событие пишется в таблицу **в той же транзакции**, что и изменение, а отдельный процесс отправляет его дальше | очередь офлайн-мутаций, которую отправляют после сохранения |
| **Очередь, джоба, воркер (BullMQ)** | задача кладётся в очередь, отдельный процесс её выполняет | Web Worker для тяжёлого: UI не ждёт |
| **jobId** | id задачи в BullMQ: задача с тем же id не создаётся, пока прежняя хранится в Redis (в том числе завершённая). Без двоеточий: BullMQ их запрещает | ключ `queryKey` для дедупликации запросов |
| **Reconciler** | периодическая проверка «всё ли доехало», которая чинит зависшее | — |
| **Circuit breaker** | после серии ошибок перестаём ходить в сломанный сервис на время и сразу отвечаем ошибкой | «не долбить упавший API, показать заглушку» |
| **Graceful degradation** | при перегрузке отключаем второстепенное (курсоры реже), основное работает | показать скелетон вместо падения страницы |
| **Rate limit / token bucket** | ограничение частоты: «ведро» токенов пополняется с постоянной скоростью, каждое действие тратит токен | `throttle` из lodash, только на сервере и для защиты |
| **fail-open / fail-closed** | при сбое проверки пропускаем всех / блокируем всех | — |

### Хранение

| Термин | Что это |
|---|---|
| **Репликация, RF** | копии БД на нескольких серверах; RF (replication factor) — их число |
| **sync / async реплика** | commit ждёт или не ждёт подтверждения от реплики (надёжность vs скорость) |
| **failover, Patroni, Sentinel** | автоматическое переключение на реплику при падении главного узла (Patroni — для Postgres, Sentinel — для Redis) |
| **Шардирование, ключ шардирования** | разрезать данные по разным серверам по ключу (у нас `board_id`) |
| **Партиционирование** | разрезать таблицу на части внутри одного сервера |
| **IOPS** | дисковых операций в секунду. Чаще всего ограничивает именно это, а не объём |
| **WAL, PITR** | журнал изменений Postgres; восстановление на любой момент времени по нему |
| **TOAST** | механизм Postgres для больших значений (`bytea`, `text`): хранит отдельно и сжимает |
| **pg_trgm** | расширение Postgres для быстрого поиска по подстроке (`ILIKE '%арх%'`) через триграммы |
| **Soft delete** | «удаление» флагом `deleted_at` вместо `DELETE` (корзина) |
| **Presigned URL** | временная подписанная ссылка в S3: браузер загружает или скачивает файл напрямую, минуя наш сервер |
| **CDN** | сеть кэширующих серверов рядом с пользователем для статики и картинок |
| **Object storage (S3)** | хранилище файлов по ключу; дешёвое, для больших неизменяемых объектов |

### Архитектура, наблюдаемость, безопасность

| Термин | Что это |
|---|---|
| **Модульный монолит** | один деплой-артефакт, но код разделён на модули с чёткими границами. У нас — три роли запуска одного кода |
| **C4** | 4 уровня диаграмм архитектуры: Context → Container → Component → Code |
| **RED** | Rate, Errors, Duration — три базовые метрики для любого сервиса |
| **p99** | 99% запросов быстрее этого значения |
| **SLO / SLI** | цель по качеству («99.9% успешных») / метрика, которой меряем |
| **JWT access / refresh** | короткоживущий токен для запросов / долгоживущий для получения нового access |
| **IDOR** | уязвимость «подставил чужой id в URL — получил чужие данные» |
| **Structured output** | режим LLM, в котором ответ гарантированно соответствует JSON Schema |
| **Prompt injection** | текст в данных («игнорируй инструкции…»), который пытается управлять моделью |
