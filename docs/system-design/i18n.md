# Локализация

> Рабочий план для русского и английского языков. Изменения REST-контракта обсуждаются отдельно по Р-47.

## Как устроено сейчас

- `packages/i18n` хранит JSON по языкам (`ru`, `en`) и неймспейсам. `common`, `errors`, `validation` предназначены для общих пользовательских текстов; `ui` — для веба; `mail` зарезервирован для писем. Сейчас `mail` пуст, потому что отправки писем в продукте ещё нет.
- `apps/web` использует `i18next` и `react-i18next`. Загружает только `common`, `errors`, `validation`, `ui`; `mail` в браузер не импортирует. Инициализация находится в `shared/lib/i18n.ts`, а не в общем пакете, поэтому пакет не зависит от React.
- При открытии страницы веб берёт сохранённый в браузере выбор языка, затем язык браузера. Для `ru-*` используется русский, для `en-*` — английский, остальные языки получают русский. Выбор сохраняется в `localStorage` под `fanera.locale`; если хранилище недоступно, язык всё равно переключается в текущей вкладке. `html.lang` следует выбранному языку.
- Namespace отделяется от ключа двоеточием: `errors:BOARD_READ_ONLY`, `ui:demo.heading`. Точка отделяет вложенные ключи внутри namespace. Язык по умолчанию и fallback — `ru`.

## Граница между сервером и клиентом

REST-контракт предусматривает `application/problem+json` с полем `code` ([rest_api.yml](api/rest_api.yml)); WebSocket-контракт — коды ошибок в ack и `connect_error` ([websocket.md](api/websocket.md)). Эти коды остаются машинными значениями без префикса namespace. Когда появится клиентская обработка ошибок, она будет выбирать текст по коду из `errors`, а для неизвестного кода использовать `errors:UNKNOWN`. HTTP-статус, повтор запроса и работа с несохранёнными правками останутся отдельной логикой ([frontend.md §4](frontend.md#4-ошибки-что-показать-пользователю)): одинаковый текст ошибки не означает одинаковое действие.

Для писем и других сообщений вне веба серверу понадобится перевод по `Me.locale`, которое уже предусмотрено в REST-контракте. При внедрении нужно уточнить приоритет между настройкой профиля и выбором в браузере, а также момент сохранения языка в профиле. До появления таких сообщений сервер не загружает переводы и не определяет язык запроса.

Текст пользователя внутри `Y.Doc`, имена досок, машинные коды и логи не переводятся.

## Как добавлять перевод

1. Выбрать namespace по назначению текста. Пользовательский текст экрана — `ui`, общий текст действия — `common`, пользовательская ошибка по коду — `errors`, сообщение валидации — `validation`.
2. Добавить один и тот же ключ в `ru` и `en`, сохраняя одинаковые параметры интерполяции (`{{name}}`, `{{count}}`).
3. Использовать ключ через `t` с нужным namespace. Не составлять ключ из непроверенного ответа сервера без запасного `UNKNOWN`.
4. Проверить оба языка и длинный английский текст в интерфейсе. Тест проверяет совпадение ключей между языками.

ESLint проверяет текстовые узлы JSX, прямые строковые выражения в JSX и литеральные `placeholder`, `title`, `alt`, `aria-label`, `aria-description` в `apps/web/src/**/*.tsx`. Для текста, который намеренно не переводится, допускается адресное отключение правила с комментарием о причине. Это не покрывает строки в переменных, Storybook `args`, ответах сервера и статическом HTML: их проверяют при ревью.

## Следующие этапы

1. Согласовать отдельно изменение `Problem`: сейчас `frontend.md` предлагает показывать `detail` для `409`, а `errors[].message` не имеет стабильного кода. До решения эти поля и REST-контракт не меняются.
2. Когда появятся реальные экраны, переводить их по частям. Не переводить компоненты, которых ещё нет.
3. При появлении профиля связать переключатель с `Me.locale`, сохранив понятное поведение для гостя и при недоступном сервере.
4. При появлении писем загрузить на сервере только нужные namespace и проверить отправку на обоих языках.
