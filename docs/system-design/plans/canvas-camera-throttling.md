# План: троттлинг положения камеры для будущего куллинга

> Контекстная заметка для задачи по оптимизации канваса.
> Не содержит готового кода — только вопросы, варианты и шаги, чтобы принять решение до реализации.

## 1. Что мы хотим

Сейчас камера обновляется в `CanvasStore` (Zustand) при каждом событии панорамирования и зума. Для последующей реализации **куллинга** (отрисовка только видимых элементов) нужна относительно свежая, но не обязательно мгновенная копия положения камеры, по которой можно вычислить видимый viewport.

Цель — уменьшить частоту записей в стор и связанные с ними подписки/React-рендеры, сохранив плавность самого канваса.

## 2. Текущее состояние (что нашли)

- Состояние камеры живёт в `apps/web/src/entities/canvas/model/canvas-store.ts`:
  - поля `camera: { x, y, scale }`;
  - экшен `setCamera(camera)` пишет напрямую в `set({ camera })`.
- Обновления камеры идут из `apps/web/src/features/board-canvas/lib/useCanvasInteraction.ts`:
  - `onWheel` — вызывает `setCamera` на каждое событие колеса;
  - `onMouseUp` после панорамирования — один раз синхронизирует позицию `Layer` со стором.
- Для панорамирования сам `Layer` двигается напрямую через `layerRef.current?.setPosition()` и `batchDraw()`, то есть рендер Konva не ждёт обновления стора.
- Утилит `throttle` / `debounce` в `apps/web` пока нет.

## 3. Какая именно проблема решается

| Источник обновления | Частота | Что происходит сейчас |
|---|---|---|
| `wheel` | 60–120 событий/с при быстром зуме | `setCamera` → подписчики `CanvasStore` → потенциальные рендеры/пересчёты |
| `pan` | каждый кадр мыши, но в стор пишется только в `onMouseUp` | уже относительно редко, но подписчики реагируют синхронно |

Без троттлинга любой компонент, подписанный на `camera`, будет перерисовываться на каждый зум. Для куллинга это особенно важно: вычисление видимых элементов может быть дорогим, и запускать его 60 раз в секунду не нужно.

## 4. Принятые решения

| Вопрос | Решение |
|---|---|
| Троттлинг vs дебаунсинг | **Throttle** — обновления во время движения нужны, чтобы куллинг не отставал сильно. |
| Одна или две камеры | **Одна** `camera` в `CanvasStore`. Все подписчики работают с одним источником правды. |
| Интервал | **100 мс** (`cameraThrottleMs: 100`). |
| Leading-вызов | **`leading: false`** — первое событие не дергает куллинг мгновенно. |
| Trailing-вызов | **`trailing: true`** — финальное положение камеры после остановки гарантированно попадает в стор. |
| Утилита | Собственная чистая функция в `shared/lib`. Без новых зависимостей. |
| Точка троттлинга | В `useCanvasInteraction.ts` — троттлится только поток событий от пользователя, остальные вызовы `setCamera` остаются синхронными. |
| Формат данных для куллинга | Пока рано решать. Оставляем `camera: { x, y, scale }`, при необходимости расширим позже. |


## 5. Предварительный план реализации

Исходя из принятых решений:

1. **Добавить константы в `apps/web/src/features/board-canvas/config/camera.ts`**:
   - `cameraThrottleMs: 100`;
   - `cameraThrottleOptions: { leading: false, trailing: true }`.

2. **Создать `shared/lib/throttle.ts`**:
   - чистая функция: `(fn, waitMs, options?) => throttledFn`;
   - `options.leading` и `options.trailing` — булевы;
   - метод `cancel()` — сбрасывает таймер, отменяет отложенный trailing-вызов;
   - метод `flush()` — немедленно выполняет отложенный вызов, если он есть.

3. **Покрыть утилиту тестами** (`shared/lib/throttle.test.ts`):
   - при `leading: false, trailing: true` и серии вызовов с интервалом меньше `waitMs` должен сработать ровно trailing-вызов с последними аргументами;
   - при вызовах с интервалом больше `waitMs` — срабатывать по расписанию;
   - `flush()` вызывает отложенный вызов немедленно;
   - `cancel()` отменяет отложенный вызов.

4. **Подключить throttle в `useCanvasInteraction.ts`**:
   - создать `throttledSetCamera` через `useMemo` (или `useRef` + ручная инициализация), чтобы инстанс не пересоздавался на каждый рендер;
   - использовать `throttledSetCamera` в `wheelHandle` вместо прямого `setCamera`;
   - в `handleMouseUp` после пана оставить обычный `setCamera`, но вызвать `throttledSetCamera.flush()` / `cancel()` перед этим, чтобы trailing-вызов не конфликтовал с явной записью;
   - в `useEffect` при размонтировании вызвать `throttledSetCamera.cancel()`.

5. **Проверить подписчиков `camera`**:
   - убедиться, что `BoardCanvas` и другие потребители не полагаются на мгновенную синхронность;
   - если появляются визуальные артефакты, вернуться к вопросу об интервале или leading-вызове.

6. **Подготовить место под куллинг** (опционально, в этом же PR или отдельно):
   - добавить селектор `selectCamera` в `entities/canvas/model/canvas-store.ts`;
   - задокументировать, что `camera` обновляется с throttle — куллинг не должен от этого ломаться.

## 6. Как проверить

- Включить в DevTools React Profiler / рендер-счётчики и покрутить зум: количество рендеров подписчиков `camera` должно упасть с десятков/сотен в секунду до ~10–20 в секунду (в зависимости от выбранного интервала).
- Юнит-тест на утилиту throttle: фиксированное время, фиксированное количество вызовов, проверка количества срабатываний.
- Юнит-тест на стор: имитация серии `setCamera` → проверка, что подписчик вызван ожидаемое число раз.

## 7. Что проверить особенно внимательно

### 7.1. Утечка таймера

Если `throttledSetCamera` создаётся внутри компонента и не отменяется при размонтировании, trailing-вызов может случиться уже после того, как компонент ушёл. Это либо утечка, либо запись в стор несуществующего состояния. Важно вызвать `cancel()` в cleanup-эффекте.

### 7.2. Конфликт trailing + явный `setCamera`

При `mouseUp` после пана происходит явный `setCamera`. Если в этот момент throttle ждёт trailing-вызов с более старым состоянием, возможен race condition: сначала запишется новое состояние из `mouseUp`, потом — устаревшее из trailing. Поэтому перед явной записью нужно либо `flush()` (выполнить trailing сразу), либо `cancel()` (отменить его).

### 7.3. Захват актуальных аргументов

Если throttle реализован так, что замыкает первые переданные аргументы, а не последние, при быстром зуме в стор запишется не финальная камера, а одна из промежуточных. В тестах обязательно проверить, что trailing-вызов получает **последние** аргументы.

### 7.4. Зависимости в `useMemo` / `useRef`

Если `throttledSetCamera` зависит от `setCamera`, а `setCamera` берётся из стора, инстанс throttle не должен пересоздаваться часто. Zustand-селекторы возвращают стабильную ссылку на `setCamera`, но стоит перепроверить через `useMemo` dependencies или `useRef`.

## 8. Связь с будущим куллингом

Куллинг, вероятно, будет:
- брать `camera` (или `viewport`) из стора;
- вычислять мировые координаты видимой области с небольшим запасом (overscan);
- фильтровать элементы `Y.Doc` по их bounding box;
- передавать только видимые элементы в Konva.

Троттлинг камеры — первая часть этой оптимизации. Важно уже сейчас не зашить в `CanvasStore` предположения о том, что `camera` всегда синхронна и точна, иначе потом придётся переписывать подписчиков куллинга.
