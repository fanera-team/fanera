# ADR 0001. ORM для Postgres: Prisma

- **Статус:** принято
- **Дата:** 2026-11-18
- **Задача:** [#32](https://github.com/fanera-team/fanera/issues/32)
- **Связано:** Р-15 в [decisions.md](../system-design/decisions.md)

## Контекст

Бэку нужен доступ к Postgres. ТЗ разрешает Prisma или TypeORM.

Важно, что именно пойдёт через ORM:

- **Через ORM — обычный CRUD** в схеме `core`: пользователи, воркспейсы, доски, участники, комментарии, приглашения. Таблицы со связями, ничего экзотического. Этот код пишет вся команда, в том числе те, кто только учится.
- **Мимо ORM — самое сложное.** Содержимое доски — это Yjs-документ в `bytea` (Р-1), а не таблица элементов, поэтому JSON для элементов доски, о котором говорится в issue, ORM не касается. Advisory lock при восстановлении версии (Р-37) и `FOR UPDATE SKIP LOCKED` в outbox (Р-11) — сырой SQL при любой ORM.

## Варианты

**Prisma.** Модели описываются в файле `schema.prisma`. Из него генерируется типизированный клиент и SQL-миграции.

**TypeORM.** Модели — TypeScript-классы с декораторами. Запросы через репозитории, `find` или QueryBuilder. Есть официальный `@nestjs/typeorm`.

Обе подходят: `bytea`, две схемы (`core`/`collab`), транзакции с уровнем изоляции и сырой SQL есть у обеих. Разница не в возможностях, а в том, как легко ошибиться в повседневном коде.

## Минусы каждого варианта

**TypeORM:**

- Типы не отражают, что реально загружено. Не загрузил связь или выбрал не все поля — TypeScript считает, что поле есть, а в рантайме там `undefined`.
- Много способов сделать одно и то же (Active Record, Data Mapper, `find`, QueryBuilder). В команде из многих людей код будет разным.
- `synchronize: true` меняет схему БД при старте в обход миграций.

**Prisma:**

- Сложные запросы — только сырым SQL через `$queryRaw`, без проверки типов.
- Нужен шаг `prisma generate`, без него нет клиента и типов.
- Prisma 7 — свежий крупный релиз (driver adapters, `prisma.config.ts`), многие примеры в интернете под старые версии.
- Нет официального модуля Nest, `PrismaService` пишем сами.

## Решение

**Prisma.** Разница между вариантами небольшая, проект работал бы на любом.

Решает то, что через ORM у нас идёт только простой CRUD, и его пишет вся команда. Минусы TypeORM проявляются как раз в таком коде, в каждом запросе. Минусы Prisma касаются сложных запросов, которые у нас и так будут на сыром SQL, и разовой настройки (`generate`, `PrismaService`). Гибкость TypeORM (QueryBuilder, разные паттерны) нам почти не пригодилась бы.

## Последствия

- `prisma generate` запускается после `pnpm install` и в CI до typecheck и сборки.
- Сырой SQL (`$queryRaw`) держим в репозиториях и покрываем тестами с настоящей БД.
- `PrismaService` подключается и отключается так же, как остальные провайдеры (`onModuleInit` / `onApplicationShutdown`).
- Версии `prisma`, `@prisma/client` и `@prisma/adapter-pg` фиксируем одинаковые и стабильные, без `latest`.
- Схема БД меняется только через миграции; к БД обращаемся только из репозиториев и сервисов, не из контроллеров.
